# Приёмка сборки 0.1.0-alpha.1

Дата подготовки: 2026-11-04. Эта запись разделяет выполненные проверки и ещё необходимые испытания.

## Выполнено локально

| Проверка | Результат |
|---|---|
| Полный набор автоматических тестов, Linux / Python 3.12 | 266 passed |
| Изоляция тестов | Временные каталоги; внешние socket-соединения запрещены тестовой фикстурой |
| Настоящий запуск `run.py` / Waitress на localhost | HTTP health, вход администратора, страницы админки и API работают |
| Клиентский сценарий | Авторизованный POST возвращает `simulated`, `confirmed=false`; устаревший GET открытия возвращает 405 |
| Остановка процесса | Ctrl+C завершил процесс с кодом 0; журнал отметил `clean_shutdown=true` |
| JavaScript | `node --check static/js/admin.js` без ошибок |

Регрессии охватывают чужой филиал, роли и CSRF, контакт и идентичность бота,
смену телефона во время запроса, отзыв и срок доступа, неполную пагинацию CRM,
независимость уведомлений, повторные callbacks, ошибки отправки, остановку,
таймауты COM и сборку сегментированных SMS.

GitHub Actions запускает тот же набор на Windows/Linux и Python 3.12/3.13.
Актуальный результат относится к конкретному commit: [Actions](https://github.com/zhalenik/gate_bot/actions).
Зелёный CI не заменяет подключение реального модема или проверку пользовательского интерфейса в мессенджере.

## Следующая приёмка владельцем

Порядок и команды: [Windows](WINDOWS.md). На каждом этапе сначала сохраняются выключенными те внешние действия, которые не проверяются.

1. Локальные демонстрационные данные: суперадминистратор и два филиала, выдача/отзыв, гостевой пропуск, логи и экспорт.
2. Telegram и MAX по одному: ссылка, собственный контакт, повторное нажатие, истечение и отзыв, переход между разрешёнными филиалами.
3. Чтение YCLIENTS: сопоставление филиалов/клиентов/записей; отменённые записи, неявка и ошибки источника. Запись в CRM запрещена.
4. Уведомления: включаются после проверки адресатов, отдельно от права открытия.
5. SIM800C: установление связи с портом, ограниченный тест звонка, короткие и длинные кириллические SMS, несколько отправителей, неполные сегменты, остановка.
6. Контейнер/TrueNAS/NPM: после локальной приёмки — запуск, persistent state, права устройства, восстановление после перезапуска, обновление и откат.

Для каждого сбоя нужны commit, время, канал, филиал, ожидаемый и фактический результат,
а также `X-Request-ID` или `command_id` при наличии. Порядок подготовки диагностики:
[OPERATIONS.md](OPERATIONS.md). Секреты, клиентские телефоны и содержимое SMS не публикуются в issues.

## Что ещё не доказано

- Работа конкретного SIM800C, питания, антенны, USB–TTL и фактического COM-порта.
- Доставка настоящего сообщения Telegram/MAX и реальный ответ API YCLIENTS: эти обращения не выполнялись при подготовке.
- Физическое открытие шлагбаума: в текущей модели отсутствует датчик подтверждения.
- Production webhook и поведение выбранного сервера/NPM; контейнерные файлы подготовлены, но не развёрнуты.
- Поведение при большой коммерческой нагрузке и нескольких процессах: текущая схема рассчитана на один runtime.
- Атомарность изменения бизнес-данных JSON и записи уведомления в SQLite при аварии между этими операциями. Это ограничение описано в архитектуре; переход к общей транзакционной БД — отдельный этап.
