# MAX и Telegram: боты GateBot

Состояние реализации: **16 ноября 2026 года, тестовая сборка**. Оба бота используют один `AccessService`. Windows polling подготовлен и проверен офлайн; проверка в настоящих мессенджерах и на физическом шлагбауме выполняется отдельно. Из этой среды реальные сообщения и команды ворот не отправлялись.

## 1. Что умеют боты

| Сценарий | Telegram | MAX |
|---|---|---|
| Начать работу | `/start`, ссылка с параметром `start` | `bot_started`, `/start`, ссылка с параметром `start` |
| Привязать персональный пропуск | Проверка токена общим сервисом | Та же проверка |
| Найти свои пропуски по номеру | Собственный контакт с совпадающим `contact.user_id` | Подписанный контакт `request_contact`, проверка HMAC |
| Введённый вручную номер | Не авторизует пользователя | Не авторизует пользователя |
| Показать несколько филиалов | Кнопки с названием филиала | Кнопки с названием филиала |
| Открыть выбранные ворота | Повторная проверка конкретного филиала и кнопки | Та же проверка |
| Показать контакт администратора | Для привязанного филиала, в том числе после истечения пропуска | То же |
| Обновить меню | Кнопка, `/menu`, `/help` | Кнопка, `/menu`, `/help` |
| Много кнопок | Страницы по 20 действий | Страницы по 20 действий |
| Уведомить об изменении доступа | Отдельная доставка через общий outbox | Собственная доставка того же события |
| Локальный запуск | Polling в потоке общего приложения | Polling в потоке общего приложения |
| Production webhook | Следующий этап развёртывания | Есть проверенный обработчик приёма; промышленное подключение — следующий этап |

Кнопки администратора берутся из текущих настроек привязанного филиала. Неактивный пропуск не разрешает звонок на ворота. Отключённый филиал не попадает в клиентское меню.

Старые текстовые клавиатуры Telegram заменены на inline-кнопки. В каждой команде сохранены идентификаторы филиала и кнопки. Одинаковые названия «Въезд» в разных филиалах больше не превращаются в одну общую команду. Телефон ворот в callback не передаётся.

## 2. Как проходит команда

1. Мессенджер передаёт событие. Адаптер извлекает именно пользователя, совершившего действие.
2. Бот принимает только личный диалог; групповые сообщения не раскрывают пропуски и не запускают ворота.
3. Кнопка содержит идентификаторы филиала и настроенного действия. Она не является подтверждением права доступа.
4. До внешних действий бот атомарно отмечает ключ события в локальной SQLite: Telegram — для команды ворот, MAX — для всех обрабатываемых событий. У Telegram ключ использует callback ID; у MAX-нажатия — ID клавиатуры, пользователя, timestamp, ID сообщения и действие вместе. Уникальность MAX `callback_id` для каждого нажатия не предполагается.
5. `AccessService.open_for_identity` заново проверяет принадлежность пропуска, филиал, срок, блокировку, существование нужной кнопки и ограничение повторных команд.
6. Только затем общий сервис вызывает драйвер. Ответ сообщает реальное состояние команды. Без датчика положения приложение не может подтверждать физическое открытие ворот.

Один и тот же числовой ID в Telegram и MAX относится к двум разным пространствам идентификаторов. Поля `tg_id` и `max_id` не смешиваются.

## 3. MAX использует собственный контракт

Контракт проверен по [официальной документации MAX](https://dev.max.ru/docs-api), [схеме OpenAPI](https://github.com/max-messenger/api-schema/blob/main/schema.yaml) и [официальным инструкциям для AI-агентов](https://github.com/max-messenger/max-agents-skill). Последние подключены как технический источник; отдельный навык в личное окружение не устанавливался.

| Операция | Формат MAX |
|---|---|
| API | `https://platform-api2.max.ru` |
| Авторизация | Заголовок `Authorization: <токен>`, без `Bearer` |
| Отправка | `POST /messages?chat_id=…` либо `?user_id=…` |
| Тело сообщения | `{"text":"…","attachments":[…]}` |
| Кнопки | Вложение `inline_keyboard` с `payload.buttons` |
| Текст входящего сообщения | `message.body.text` |
| Автор входящего сообщения | `message.sender.user_id` |
| Автор нажатия | `callback.user.user_id` |
| Данные кнопки | `callback.payload` |
| Ответ на нажатие | `POST /answers?callback_id=…`, JSON с `notification` и/или `message` |
| Первое открытие бота | `bot_started`; контекст ссылки находится в корневом `payload` |
| Контакт | Вложение `contact` с `vcf_info`, `hash`, необязательным `max_info` |
| Временные метки событий | Миллисекунды Unix |

Исходники методов: [отправка сообщений](https://dev.max.ru/docs-api/methods/POST/messages), [ответ на callback](https://dev.max.ru/docs-api/methods/POST/answers), [объект Update](https://dev.max.ru/docs-api/objects/Update).

### Подтверждение телефона

Кнопка MAX имеет тип `request_contact`. При её использовании платформа передаёт проверяемую подпись контакта. GateBot сравнивает `hash` с:

```text
HMAC-SHA256(ключ = токен бота, сообщение = точная строка vcf_info)
```

Сравнение выполняется через `hmac.compare_digest`. Сначала проверяется подпись, затем разбирается VCF и нормализуется телефон. Нельзя сначала менять переносы строк, пробелы или имя контакта: это изменит подписанные байты. После JSON-декодирования `\r\n` уже являются настоящими переносами строк.

Контакт без подписи, пересланное сообщение, несовпадающий `max_info.user_id` и VCF с неоднозначными номерами не привязывают аккаунт. Это механизм Bot API; алгоритмы подписи мини-приложений и MAX Bridge здесь не используются. Основание: [официальное описание request_contact](https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard).

### Персональная ссылка

Формат:

```text
https://max.ru/<имя_бота>?start=<токен_пропуска>
```

Бот обрабатывает `bot_started.payload`. Длина параметра бота ограничена 128 символами; `startapp` относится к мини-приложениям и в этом сценарии не используется. GateBot не перезаписывает чужую существующую привязку. Источники: [диплинки](https://dev.max.ru/help/deeplinks), [сценарии Bot API](https://dev.max.ru/docs/chatbots/bots-coding/prepare/).

## 4. Локальный запуск в Windows

Основной запуск — `run.py`: он владеет веб-сервером, двумя polling-процессами обработки, планировщиком и модемом. Не запускайте одновременно `run.py` и отдельные `telegram_bot.py` / `max_bot.py` с теми же токенами.

PowerShell, из каталога проекта:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Если `.env` ещё нет, создайте его из `.env.example`. Существующий заполненный `.env` не перезаписывайте. Для первого теста настройте локально:

```dotenv
BOT_ENABLED=true
BOT_MODE=polling
BOT_TOKEN=
BOT_USERNAME=

MAX_BOT_ENABLED=true
MAX_BOT_MODE=polling
MAX_BOT_TOKEN=
MAX_BOT_USERNAME=
MAX_API_BASE_URL=https://platform-api2.max.ru
MAX_CA_BUNDLE=

GATE_DRY_RUN=true
SIM800_ENABLED=false
OUTBOUND_ENABLED=false
```

Пустые значения токенов и имён необходимо заполнить. В загруженном архиве MAX действующего токена не было: там находился только пример конфигурации. Токены задаются в вашем `.env` и не входят в публичный репозиторий.

```powershell
.\.venv\Scripts\python.exe run.py
```

`GATE_DRY_RUN=true` оставляет управление в проверочном режиме: можно проверить привязку, филиалы, кнопки и отказ в доступе без звонка. `OUTBOUND_ENABLED=false` отключает автоматические исходящие уведомления; ответы бота на ваши действия продолжают работать. Для отдельной проверки уведомлений включается `OUTBOUND_ENABLED` и рассылка у соответствующего тестового пропуска.

При необходимости изолированной отладки допускаются отдельные команды:

```powershell
.\.venv\Scripts\python.exe max_bot.py
.\.venv\Scripts\python.exe telegram_bot.py
```

Эти команды запускают только один транспорт. Они также требуют соответствующего `BOT_ENABLED=true` или `MAX_BOT_ENABLED=true`. Они не заменяют общий supervisor и его обработчик автоматических уведомлений.

Каждый polling-транспорт удерживает блокировку по платформе и отпечатку токена в общем временном каталоге ОС. Поэтому другой каталог `GATEBOT_DATA_DIR` не позволяет запустить второй polling того же бота в этой среде. В имени файла блокировки токена нет. Это локальная блокировка: раздельные временные каталоги пользователей, контейнеров и разные серверы не образуют общую блокировку. Для одновременной Windows-проверки и работающего сервера нужны разные тестовые и рабочие боты.

### Сертификат для MAX API

Актуальный MAX API использует новый хост и требует доверия соответствующему корневому сертификату. `MAX_CA_BUNDLE` позволяет указать файл PEM для исходящих MAX-запросов. Если среда уже доверяет цепочке, значение можно оставить пустым.

Для дополнительного сертификата используйте проверенный PEM bundle с обычными доверенными корнями и требуемым корнем. Не отключайте проверку TLS. Путь Windows может выглядеть как `C:/GateBot/certs/max-ca-bundle.pem`. Конкретный сертификат и его отпечаток проверяются по [официальной инструкции MAX по TLS](https://github.com/max-messenger/max-agents-skill/blob/main/references/tls-trust.md). Эта настройка относится к исходящему API и не заменяет сертификат домена будущего webhook.

Если `manage.py check-bots --platform max` вернул `tls_trust_failed`, выполните из
корня проекта следующие команды PowerShell. Они скачивают только публичный
корневой сертификат с официального адреса; токен в командную строку не передаётся:

```powershell
New-Item -ItemType Directory -Force .\private | Out-Null
Invoke-WebRequest -Uri "https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt" -OutFile .\private\max-root.crt -TimeoutSec 30
```

Сверьте SHA-256 отпечаток **сертификата**, а затем создайте отдельный bundle для MAX.
Следующий блок делает это целиком. Отпечаток взят из официального TLS-руководства
MAX, проверенного 16.11.2026. При несовпадении файл не принимается; проверьте актуальное
руководство вместо отключения сравнения. Это не SHA-256 текстового PEM-файла:

```powershell
@'
from pathlib import Path
import hashlib
import ssl
import certifi

root = Path('private/max-root.crt').read_text(encoding='ascii').strip()
actual = hashlib.sha256(ssl.PEM_cert_to_DER_cert(root)).hexdigest()
expected = 'd26d2d0231b7c39f92cc738512ba54103519e4405d68b5bd703e9788ca8ecf31'
if actual != expected:
    raise SystemExit('Certificate fingerprint mismatch: check the official MAX TLS guide.')
bundle = Path('private/max-ca-bundle.pem')
bundle.write_bytes(Path(certifi.where()).read_bytes() + b'\n' + root.encode('ascii') + b'\n')
ssl.create_default_context(cafile=str(bundle))
print('Verified MAX CA bundle created: private/max-ca-bundle.pem')
'@ | .\.venv\Scripts\python.exe -
```

Только после успешного сообщения добавьте или измените в `.env`:

```dotenv
MAX_CA_BUNDLE=private/max-ca-bundle.pem
```

Повторите `manage.py check-bots --platform max`. Эта настройка применяется только
к HTTP-клиенту MAX и сохраняет проверку TLS. Системное хранилище Windows, Telegram
и YCLIENTS она не меняет. Корневой сертификат не требуется публиковать в Git.

## 5. Состояние, повторы и остановка

`data/bot_state.sqlite3` содержит отдельные checkpoints и обработанные события ботов. Файл создаётся только при запуске/создании runtime, использует WAL и атомарные операции SQLite. Пространство данных зависит и от платформы, и от отпечатка токена, поэтому смена тестового бота не переиспользует чужой cursor. Событие получает состояние `claimed`, затем `handled`, `failed`, `unknown` или `cancelled`. `handled` означает завершение обработчика; подтверждением физического открытия оно не является. В записи сохраняются только отпечаток события, время и безопасный код ошибки.

MAX возвращает `marker` следующей порции событий. GateBot сохраняет его после обработки порции, передаёт ровно полученное значение и не увеличивает его как Telegram offset. Ошибка безопасного `GET /updates` оставляет checkpoint прежним и не помечает ещё не полученные события. При ошибке отправки обработчик сохраняет результат события и оставляет прежний marker до следующей успешной обработки порции. Повторно полученное событие с уже сохранённым claim не отправляется заново; после пропуска этого события порция может быть завершена и checkpoint продвинут. Постоянный отказ отдельного получателя не останавливает остальных пользователей. В документации MAX и OpenAPI расходится описание первого запроса без marker; историческое восстановление до первого checkpoint не гарантируется. [Правила Long Polling](https://dev.max.ru/docs-api/methods/GET/updates).

Для всех MAX-событий принят принцип **не более одной попытки внешних действий обработчика**: подпись контакта, привязка и ответы выполняются после claim. Таймаут `POST` может означать, что сообщение уже доставлено. В этом случае событие остаётся с результатом `unknown`, автоматический повтор отсутствует. В редком сбое между claim и фактической отправкой пользователь может не получить ответ; он может заново вызвать `/menu`, отправить свой контакт или открыть персональную ссылку. Это осознанный компромисс между потерянным ответом и повторными действиями.

Для звонка принят принцип **не более одного автоматического выполнения одного нажатия**. Если приложение остановилось между фиксацией нажатия и отправкой команды модему, оно не станет автоматически повторно звонить после перезапуска. Клиент может нажать кнопку ещё раз; это новое событие с новой проверкой доступа. Повторное нажатие на прежнюю клавиатуру MAX отличается временной меткой даже при прежнем `callback_id`. Окончание HTTP-запроса или процесса не является доказательством движения ворот.

MAX-команда старше двух минут отклоняется. Возраст берётся из timestamp нажатия. У Telegram callback нет собственной временной метки: дата старого сообщения меню не используется как дата нажатия. При старте Telegram polling удаляются накопленные удалённые обновления, чтобы не выполнять давние команды ворот. Локальные access-уведомления в outbox этим не удаляются.

Перед запуском оба бота проверяют существующие webhook-настройки. При найденном webhook polling не начинается; действующая подписка не удаляется автоматически. Это позволяет случайным запуском на Windows не отключить работающий сервер.

Остановка проверяется после long polling и перед передачей команды общему сервису. Уже полученные, но ещё не выполненные команды ворот MAX отмечаются как `cancelled` и не исполняются при повторном чтении порции. `running` в статусе означает, что цикл запущен, а `ready` устанавливается после успешного запроса обновлений, сбрасывается при ошибке опроса и восстанавливается после следующего успешного запроса. Это последнее наблюдаемое состояние транспорта, а не гарантия доставки следующего сообщения. При остановке оба флага сбрасываются.

Автоматические уведомления хранятся в общей очереди приложения с отдельными получателями Telegram и MAX. Режимы `failed`/неопределённого результата не означают доставку. В текущем outbox нет слепой автоматической переотправки после неоднозначной ошибки отправки. Состояние нужно смотреть в диагностике; для следующего этапа предусмотрено управляемое повторение.

## 6. Диагностика

`manage.py doctor` проверяет только локальную конфигурацию. Для реального соединения:

```powershell
.\.venv\Scripts\python.exe manage.py check-bots --platform max
.\.venv\Scripts\python.exe manage.py check-bots --platform telegram
```

Проверка читает профиль бота и метаданные webhook, не потребляет updates, не отправляет
сообщения и не обращается к CRM/COM. `status=ok` — успешная предварительная проверка,
а не подтверждение запуска polling. Ошибка содержит безопасные поля `error_code`,
`http_status`, `stage`, `action`; их можно прислать для разбора. Боди ответа API,
значения токенов, URL webhook и профиль бота не выводятся. При ошибке код завершения 1.
`run.py` теперь показывает эти код/этап/HTTP-статус прямо в консоли.

`max_username_missing` не означает неверный токен: это отсутствие `MAX_BOT_USERNAME`
для формирования ссылок. Авторизация MAX выполняется токеном. При успешном запросе
проверка показывает булево `configured_username_matches`, чтобы обнаружить опечатку
или никнейм другого бота. Указание отображаемого названия вместо никнейма не подходит.

| Симптом | Что проверить |
|---|---|
| `tls_trust_failed` | Корректность `MAX_CA_BUNDLE`, цепочку доверия нового API-хоста |
| `ca_bundle_invalid` | Путь к существующему читаемому PEM-файлу из раздела выше |
| `token_invalid_format` | Только токен в `MAX_BOT_TOKEN`, без `Bearer`, заголовка и перевода строки |
| `connect_timeout`, `read_timeout`, `timeout` | Сеть/VPN, доступ к API; сервер не дал ответ в срок |
| `dns_error`, `proxy_error`, `connection_error` | DNS, прокси, соединение или разрыв соединения |
| HTTP 401 MAX | Локальный MAX-токен, правильный тип токена и его актуальность |
| Polling отказался запускаться с `active_webhook` | У бота есть зарегистрированный webhook; используйте отдельного тестового бота или явно переключите его режим |
| `polling_already_running` | Другой локальный процесс уже удерживает polling этого токена; проверьте отдельный запуск бота и `run.py` |
| `running=true`, `ready=false` | Первый опрос ещё не завершился или последний опрос завершился ошибкой; проверьте события `BOT_POLL_ERROR` и последующее `BOT_POLL_READY` |
| Бот отвечает, пропусков нет | Привязку к своему контакту/персональной ссылке, филиал и сроки в GateBot |
| Контакт отклонён | Нажать именно кнопку запроса своего контакта, а не отправлять номер текстом или через вложения |
| Команда ворот отклонена | Активность пропуска конкретного филиала, текущую кнопку, cooldown, для MAX возраст нажатия |
| «Команда принята», а ворота не двигались | Поле `delivery`, режим dry run, состояние драйвера и журнала команд; подтверждение датчиком отсутствует |
| Нет автоматического уведомления | `OUTBOUND_ENABLED`, рассылку у клиента, привязку нужной платформы, готовность бота и запись outbox |

События ботов сохраняются через общий структурированный журнал `logger.event`: запуск и остановка, ошибка и восстановление опроса, отказ API, результат команды и ошибка уведомления. Журнал не получает токен, полный raw update, VCF и тело ошибки API. Диагностика использует платформу, тип события, безопасный код ошибки, HTTP-статус, отпечаток события и ID команды. Сторонние Telegram/HTTP-логи подавлены: их URL и тексты исключений могут содержать токен; вместо них сохраняется безопасный тип ошибки.

## 7. Проверки перед переходом к серверу

Офлайн-тесты покрывают wire-формат MAX, проверку собственного контакта, типы событий, разделение ID, scoped callback, повторную доставку, checkpoints, ограничения меню, приватность диалогов, Windows-совместимый запуск asyncio в потоке, отказ от удаления webhook и проверку входящего секрета. Дополнительно проверяются запрет второго polling одного токена при разных каталогах данных, enabled-флаги standalone-запуска, переходы готовности после сетевой ошибки, отсутствие повторного `POST` после неопределённого результата и отмена команды при остановке. Все внешние вызовы в них заменены тестовыми объектами.

На Windows отдельно проверить с тестовыми аккаунтами:

1. `/start`, собственный контакт, персональную ссылку и повторный запуск приложения.
2. Два филиала с одинаковым названием кнопки, активный пропуск только в одном из них.
3. Истечение и отзыв пропуска при открытом старом меню: старое сообщение не разрешает доступ.
4. Контакт администратора после истечения пропуска.
5. Повторное нажатие, cooldown и повторную доставку одного callback.
6. Grant/revoke-уведомления отдельно в Telegram и MAX.
7. Остановку и запуск при отключённой сети, затем восстановление связи.
8. После dry run — отдельную проверку настоящего модема и ворот по инструкции SIM800C.

## 8. Будущий webhook через Nginx Proxy Manager

MAX официально выделяет polling для разработки/тестов и webhook для production. Они не работают одновременно. Production endpoint должен быть доступен по HTTPS на порту 443, с доверенной цепочкой сертификатов, и отвечать HTTP 200 не позднее 30 секунд. Секрет передаётся в `X-Max-Bot-Api-Secret`. [Требования MAX](https://dev.max.ru/docs-api/methods/POST/subscriptions).

`register_webhook(app, bot, secret=..., enqueue=...)` проверяет этот заголовок и отдаёт 200 после успешного сохранения события через переданную durable enqueue-функцию. Функция не регистрирует внешнюю подписку и не запускает обработчик очереди. Готовность этого HTTP-обработчика сама по себе **не означает готовность production webhook**: ещё требуются общий durable inbox, worker, интеграция с supervisor, прокси и реальная проверка повторной доставки. Эти задачи относятся к следующему серверному этапу.

Не включайте несколько polling-потребителей одного токена или параллельные экземпляры приложения с одним COM-портом. Текущий supervisor владеет ресурсами одного экземпляра. Масштабирование потребителей и распределение модемов между серверами требуют отдельной схемы владельцев устройств.

## 9. Правила дальнейшей разработки MAX

При изменениях сначала проверять актуальные официальные методы, объект Update и [MAX Agent Skill](https://github.com/max-messenger/max-agents-skill/blob/main/SKILL.md). Затем добавлять обезличенный fixture и тест конкретного сценария. Содержимое реальных контактов и токены в fixtures не сохраняются.

Исходный community-шаблон найден: [MaxApiDevs/max-bot-aio-template](https://github.com/MaxApiDevs/max-bot-aio-template). Его `.cursorrules` и февральские примеры объясняют происхождение исходной попытки. Их ограничения не перекрывают более новые официальные сведения. Успешный echo-тест через `maxapi` подтверждал работу отдельного polling-примера, но не проверял второй, Flask-клиент: в нём были неверные заголовок Authorization, тело отправки, ответ на callback и секрет webhook. Текущий адаптер проверяет эти места самостоятельными контрактными тестами.

Основные файлы:

| Файл | Ответственность |
|---|---|
| `access_service.py` | Единые правила привязки и допуска к конкретным воротам |
| `max_api.py` | Собственный HTTP-контракт MAX, TLS, таймауты и безопасные ошибки |
| `max_bot.py` | MAX updates, контакт HMAC, меню, polling и заготовка webhook-приёма |
| `telegram_bot.py` | Telegram handlers и asyncio lifecycle |
| `bot_state.py` | Атомарные claims, результаты обработки и checkpoints обоих ботов |
| `polling_lock.py` | Локальная блокировка polling по платформе и отпечатку токена |
| `notifications.py` | Автоматические исходящие уведомления и связь с outbox |
| `run.py` | Единственный владелец runtime-потоков |
