# Эксплуатация, журнал и поддержка

## Запуск и остановка

Используйте `python run.py`. Один процесс владеет фоновой работой и устройством. Повторный процесс с тем же каталогом данных отклоняется. Polling одного и того же токена нельзя одновременно запускать на Windows и сервере: токен — одна очередь обновлений. `app.py` и импорты модулей не являются способом запуска всей системы.

Ctrl+C прекращает приём команд, затем останавливает polling, планировщик и отправку, отменяет ожидающую очередь модема и освобождает порт. Не запускайте Flask reloader или несколько WSGI workers рядом с этим runtime.

Первый запуск обновлённого `run.py` получает `data/runtime.lock`, затем переносит `branches.json`, `links.json` и `admins.json` в `data/application.sqlite3`. До активации сохраняется копия исходных JSON и контрольные суммы в `data/migration-backups/`; маркер `data/.sql-active` появляется только после успешной транзакции. После этого JSON остаются архивом, изменения выполняются в SQLite. Не редактируйте старые JSON в расчёте изменить работающую систему и не удаляйте маркер ради отката. Повторный запуск не импортирует устаревший JSON поверх БД.

Номера, токены пропусков, текущие ручные права и старые хеши паролей сохраняются. Записи без телефона остаются для исправления, но не получают новую привязку бота. Отдельные люди с совпадающим телефоном при импорте автоматически не сливаются. У аккаунта администратора появляется связанный клиент, а права филиала хранятся отдельно от его обычного пропуска.

## Вход и восстановление администратора

На странице `/admin/login` вводится **логин из `--username`**. Параметр `--name` задаёт только отображаемое имя и поддерживает кириллицу. Например, у аккаунта, созданного с `--username owner --name "Суперадминистратор"`, логин — `owner`. Повторная команда создания существующего аккаунта не меняет его пароль.

Команды выполняются локально из корня проекта. В PowerShell вместо `python` используйте `.\.venv\Scripts\python.exe`.

```text
python admin.py --list
python admin.py --reset-password --username owner
python admin.py --username owner --name "Суперадминистратор" --super --phone PHONE
python admin.py --link-person --username owner --phone PHONE
```

`PHONE` заменяется личным номером владельца с кодом страны. Новая консольная учётная запись требует телефон; формы регистрации и SMS-код для суперадминистратора не нужны. `--link-person` связывает существующий аккаунт с явно указанным телефоном; дополнительный `--client-token` позволяет явно выбрать уже существующего клиента с тем же номером. До миграции SQLite команды изменения требуют остановленного runtime. После миграции они используют транзакции БД. Пароль по-прежнему вводится скрыто, в аргументах его нет.

Необязательная приватная настройка `BOOTSTRAP_SUPERADMIN_PHONE` связывает единственный старый аккаунт суперадминистратора без личности при следующем запуске. Уже связанный аккаунт не переназначается; клиент выбирается только по однозначному точному совпадению указанного телефона. Значение не включают в Git и диагностику. Если привязки нет, веб-вход старого аккаунта сохраняется, а подключение администраторских функций бота предлагает сначала указать телефон через консоль.

`--list` показывает логины, отображаемые имена, роли, филиалы и состояние отключения без хешей паролей. Это приватные сведения установки: вывод не добавляют в публичный репозиторий или Issue. `--reset-password` дважды запрашивает новый пароль в терминале, меняет пароль только указанного аккаунта и отзывает его прежние веб-сессии. Имя, роль, филиал и признак отключения сохраняются. Пароль должен содержать от 12 до 1024 символов; его не передают аргументом командной строки.

Если до миграции `admins.json` очистили вручную или повредили, остановите `run.py` и выполните явное восстановление:

```text
python admin.py --recover --username owner --name "Суперадминистратор" --super
```

До изменения существующего файла команда сохраняет его исходные байты рядом с ним в `admins.json.recovery-<timestamp>-<random>.bak`. Если резервную копию записать не удалось, восстановление прекращается. Файл резервной копии содержит приватные данные и хранится вне Git вместе с `data/`.

После миграции `--recover` сохраняет приватный снимок актуального документа аккаунтов из SQLite в такой же backup-файл. Это восстановление учётной записи, а не ремонт повреждённой SQLite. При повреждении БД восстанавливают согласованную резервную копию всего каталога данных. Смена пароля отзывает веб-сессии и ещё не использованные ссылки подключения административного бота.

При исправном JSON остальные аккаунты сохраняются: отсутствующий `owner` создаётся, существующий суперадминистратор `owner` получает новый пароль и включается. Команда откажется менять роль существующего администратора филиала на супер-роль; для обычной смены пароля используется `--reset-password`. Если весь JSON не читается, создаётся новое хранилище с указанным аккаунтом, а исходный файл остаётся в резервной копии для отдельного разбора. Данные клиентов и филиалов эта операция не меняет. Обычный запуск и команда создания не исправляют повреждённый JSON автоматически.

После восстановления запустите приложение и войдите под `owner` с новым паролем. Для другой установки подставьте её нужный логин и роль. UTF-8 с BOM читается штатно и само по себе не считается повреждением.

## Что пишет журнал

`data/logs/events.jsonl`: JSON-события с `ts`, `level`, `event`, `branch_id`, псевдонимом `actor`, `correlation_id`, безопасными `details`. Ротация: до 5 MiB на файл, пять резервных файлов. Фактическая глубина истории зависит от нагрузки; срок хранения в днях пока не обещается.

Ключевые события: вход и действия администратора, выдача/отзыв прав, результат синхронизации филиала, отказ/принятие команды ворот, состояние очереди модема, отправка/ошибка уведомления, запуск и остановка runtime. Телефоны, персональные токены, пароли, cookies, authorization headers и содержимое SMS не пишутся в журнал. Бизнес-данные остаются в приватном состоянии и не копируются в support bundle.

При HTTP-ошибке сохраняйте `X-Request-ID`; при команде ворот — `command_id`. Запрос, решение доступа и физическое выполнение являются разными этапами. Отсутствие записи о физическом открытии нормально: датчика положения ворот нет.

## Диагностика

```text
python manage.py doctor
python manage.py support-bundle --output data/support-bundle.zip
python manage.py support-bundle --branch 1001 --output data/branch-support.zip
```

`doctor` описывает установленные версии, количество записей/филиалов, режимы интеграций и состояние уведомлений. Он не делает запросов в сеть и не опрашивает железо. `local_config=ok` означает локальную проверку конфигурации, а не работоспособность токена, оператора или устройства.

Для отдельной проверки связи с API ботов:

```text
python manage.py check-bots --platform max
python manage.py check-bots --platform telegram
```

Эти команды читают сведения о боте и его webhook-подписках. Они не запускают polling, не забирают обновления, не отправляют сообщения, не меняют webhook, не обращаются к YCLIENTS или модему. Проверяются включённые в конфигурации боты; отключённый бот получает `status=skipped`. Без `--platform` проверяются обе платформы.

Отчёт содержит безопасные `error_code`, `http_status`, `stage` и рекомендацию `action`, а также признаки наличия/совпадения имени. Токены, фактические имена ботов, URL webhook и сырые ответы API не выводятся. Успешная проверка подтверждает чтение метаданных в данный момент; полноценный приём обновлений проверяется отдельно по `BOT_POLL_READY` после запуска `run.py`.

Support bundle содержит только `diagnostics.json`, последние маскированные события и описание состава. Даже после маскирования в нём остаются branch IDs и время событий; просмотрите файл перед передачей. Никогда не добавляйте архив bundle в публичный репозиторий.

## Диагностическая карточка проблемы

Владелец/администратор передаёт: commit/версию; дата и время с часовым поясом; branch_id; канал; ожидаемый результат; фактический текст ошибки; request/command ID; воспроизводится ли повторно; наличие изменённых настроек и версия последней рабочей сборки. Токены, пароли, полные номера и текст SMS в карточку не входят.

## Разбор типичных состояний

| Симптом | Проверить |
|---|---|
| Нет пропуска | Филиал, gate_access, admin_blocked, срок и часовой пояс, источник manual/appointment, последний успешный sync |
| В браузере есть доступ, в боте нет | Подтверждённую привязку нужной платформы; смена телефона намеренно сбрасывает связи |
| Команда принята, ворота не открылись | simulated/queued, command_id, очередь/TTL, serial/оператор. Не считать accepted подтверждением положения |
| MAX не соединяется | Актуальный hostname, наличие токена, доверенный CA bundle, активный webhook/другой poller; TLS verification не отключать |
| CRM недоступна | Наличие credentials для exact branch, HTTP-код/тип ошибки, статус полного снимка. Пустая ошибка не должна отзывать права |
| Сообщение не пришло | mailing_enabled, OUTBOUND_ENABLED, связь бота, readiness, pending/failed/unknown; состояние ChatPush |
| COM занят | Второй runtime/standalone tool, точный порт, права пользователя/группы, завершён ли прошлый процесс |
| Длинное SMS неполное | Сохранить обезличенные PDU и технические метаданные сегментов; проверить, что все части вообще присутствуют на SIM |

## Уведомления и неопределённость

Outbox сохраняет состояния pending/sending/sent/failed/unknown. В этой версии нет автоматического retry неоднозначной отправки: это предотвращает повторную рассылку после timeout. Для физической команды применяется тот же принцип — неизвестный результат не является основанием немедленно позвонить ещё раз.

После миграции изменение пропуска и добавление задания уведомления выполняются в общей транзакции SQLite. Ошибка формирования outbox откатывает изменение; таймаут уже начатой внешней отправки остаётся `unknown`. Режим совместимости с неактивированным JSON предназначен для миграции и старых offline-тестов, а не для нового рабочего runtime.

## Приглашения, подключения и уведомления

В `/admin/invitations` администратор выбирает свой филиал, создаёт приглашение на час, видит приглашения и действующих администраторов, отзывает права. Принимающий приглашение подтверждает телефон кодом SIM800 (5 минут, 5 попыток, не чаще раза в минуту) и создаёт учётную запись либо подтверждает пароль существующей. Имитация SMS не активирует код. Снятие роли убирает только постоянный административный пропуск, сохраняя отдельные ручные/CRM права; явная блокировка клиента приоритетнее роли.

`/register-branch` создаёт кабинет нового филиала после проверки телефона. В сценарии YCLIENTS до проверки суперадминистратором филиал отключён для команд ворот; trial начинается при активации. В сценарии «Без CRM» ID назначается сервером, кабинет активируется сразу после SMS-проверки и получает два календарных месяца trial без квоты. В обоих сценариях новая регистрация имеет пустой список ворот, аппаратные маршруты задаёт суперадминистратор. Регистрация уже существующего ID отклоняется; существующие администраторы используют приглашения.

Тип филиала хранится в `yclients_enabled`; отсутствие поля означает прежний режим YCLIENTS. Самостоятельным филиалам сервер выделяет числовые ID из последовательности от `10^12`, проверяя занятые и ожидающие регистрацию ID в одной SQLite-транзакции. Пропущенные после отмены регистрации значения не переиспользуются. Поле `id_origin=internal` запрещает включить CRM под внутренним номером; текущие ссылки, клиенты и права при изменении обычных настроек не перенумеровываются. Планировщик не запрашивает CRM для самостоятельного филиала и не применяет пустой CRM-снимок к его ручным правам.

В `/admin/notification-settings` задаётся матрица событий и каналов email/Telegram/MAX. Email подтверждается отдельной ссылкой. Административная привязка бота создаётся из авторизованного кабинета: ссылка действует 10 минут и используется один раз. Обычная персональная ссылка клиента не даёт административных прав. Входящие звонки/SMS доступны только суперадминистратору. Изменение телефона отзывает привязки ботов; новый телефон требует явного подтверждения личности.

В `/admin/integrations` YCLIENTS подключается по логину/паролю с 2FA. Пароль используется только на текущем запросе формы и не сохраняется. Этот мастер имеет единственную операцию авторизации; рабочий CRM-клиент по-прежнему допускает только разрешённые GET и не изменяет CRM. Наши автоматические проверки используют подставной transport, реальный auth POST не выполняется. Для ChatPush здесь достаточно токена: после сохранения уведомления отправляются через `POST https://api.chatpush.ru/api/v1/delivery` с `phone`/`text` и сырым токеном в `authorization`. Сохранение не выполняет запрос к провайдеру. Старый `/admin/chatpush` и мастер scope/QR удалены; повторная авторизация мессенджеров в GateBot не требуется.

Интеграционные токены и содержимое outbox зашифрованы. Ключ `data/integration.key` хранится отдельно от БД и обязателен для восстановления. Не копируйте токены, OTP, содержимое SMS и SQL-дампы в Git, логи или Issue.

### Временная локальная доставка кодов регистрации

Для локальной приёмки существует выключенное по умолчанию перенаправление:
`DEV_REGISTRATION_SMS_REDIRECT_ENABLED`, `DEV_REGISTRATION_SMS_PREFIX`,
`DEV_REGISTRATION_SMS_PHONE`. Реальные префикс и получатель задаются только
в приватной `.env`. Нужен явно заданный `GATEBOT_ENV=development`; production,
staging и отсутствие явно заданного окружения не включают перенаправление даже
при сохранённом флаге. Неверная настройка в development останавливает отправку.

Перенаправляются только коды регистрации филиала и принятия приглашения админа.
Исходный номер остаётся номером аккаунта и участвует в лимитах. Приглашения со
ссылкой, QR-вход, обычные SMS и остальные каналы отправляются как прежде.
Код остаётся обязательным, имеет прежние срок/лимиты, проходит очередь SIM800 и
попадает в приватную переписку фактического получателя. Сервер сохраняет HMAC
маршрутизации: выключение опции, смена окружения/префикса/получателя запрещает
использование уже выданного перенаправленного кода.

Перед production удалить эти три настройки и использовать
`GATEBOT_ENV=production`. Завершённые тестовые регистрации автоматически не
удаляются: тестовую базу и тестовые аккаунты не переносить в рабочий контур.

## Резервная копия и откат

1. Остановить runtime и убедиться, что порт освобождён.
2. Скопировать весь private data directory: `application.sqlite3`, `runtime.sqlite3`, оставшиеся `-wal`/`-shm`, маркер `.sql-active`, `integration.key`, `session.key` при его использовании, журнал телефонии, остальные приватные JSON и архивы миграции. Отдельно сохранить защищённый `.env`. Не копировать один SQLite-файл из работающего процесса: нужна согласованная копия после остановки либо SQLite backup API.
3. Хранить резервные копии вне публичного репозитория с ограниченными правами.
4. Восстанавливать сначала в отдельный каталог с отключёнными интеграциями и `GATE_DRY_RUN=true`.
5. Запустить doctor, проверить обе роли, число записей, токены, срок доступа, подписки/квоты и расшифровку подключений. Сохранять `.sql-active` вместе с БД: без маркера можно случайно вернуться к устаревшему JSON.
6. Запуск реальных сервисов только после проверки; обновление кода не должно затирать `data/`.

Для контейнера применять фиксированный проверенный image tag. `pull_policy: always` обновляет образ при пересоздании/запуске согласно TrueNAS, но не является обещанием бесшовного автоматического обновления работающего процесса.
