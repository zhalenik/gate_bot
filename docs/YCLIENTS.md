# YCLIENTS: чтение и локальные права

## Неподвижное ограничение

При разработке действующую CRM разрешено только читать. В `YClientsClient.request` разрешён только `GET` по явному списку относительных путей текущего филиала. Отправка SMS, создание/редактирование/удаление записей и клиентов, вход через `POST /auth`, регистрация webhook и любые произвольные endpoints запрещены этим reader.

Отдельные мастера подключения не расширяют allowlist reader и не дают разрешения на реальные изменения при разработке. Сценарий установки через маркетплейс реализован и проверен с подменённым API; флаг установки по умолчанию выключен. Порядок настройки карточки, системного пользователя и HTTPS-адресов — [YCLIENTS_MARKETPLACE.md](YCLIENTS_MARKETPLACE.md). Его callback отключения приложения отличается от webhook записей ниже.

Для расписания используется `GET /records/{company_id}`, для [поиска ID клиента по телефону](YCLIENTS_CLIENT_IDS.md) — `GET /clients/{company_id}`; предусмотрено чтение `GET /client/{company_id}/{client_id}`. Чтение сотрудников внесено в allowlist для последующего этапа, но автоматический импорт сотрудников не запущен. Redirects отключены; HTTPS проверяется. Допускаются только официальные API-hosts `api.yclients.ru` и `api.yclients.com`, без credentials в URL.

В [официальной API-документации](https://developers.yclients.com/ru/) метод `GET /clients/{company_id}` помечен устаревшим. Он поддерживает фильтр `phone` и пагинацию `page`/`count`; GateBot проверяет точное совпадение полного нормализованного телефона после получения всех страниц. Современный `POST /company/{company_id}/clients/search` не используется: автоматического перехода на POST при отказе GET нет. Ошибка поиска сохраняет локальную карточку и её права.

## Два способа подключения

**Учётная запись YCLIENTS** — самостоятельная регистрация на сайте GateBot с ID
филиала. После SMS-проверки и задания пароля кабинет сразу активен. Администратор открывает «Интеграции» и входит с логином
и паролем обычного пользователя YCLIENTS, имеющего доступ к этому филиалу. Установка
приложения из маркетплейса для этого способа не требуется. GateBot автоматически
получает токен, проверяет права и сохраняет его зашифрованно для выбранного филиала.
Пароль YCLIENTS и двухфакторный код не сохраняются.

**Приложение YCLIENTS Marketplace** — регистрация из карточки приложения по подписанному `user_data`. Пользователь выбирает один из переданных салонов. GateBot проверяет связь профиля с филиалом по подписанным идентификаторам и активную установку приложения. Форма подставляет название салона, имя, телефон и email. Новый администратор может исправить их, подтверждает телефон по SMS и задаёт пароль GateBot. При замене корректного номера из профиля YCLIENTS он подтверждает исходный и новый номера. Для прежнего или впервые указанного номера достаточно одного SMS-кода. Затем создаются филиал, клиентская карточка администратора, подключение системного пользователя и первый пробный период. Существующий пользователь входит с прежним паролем. Для новой регистрации в Marketplace включите передачу данных пользователя в карточке приложения. Самостоятельная регистрация по ID филиала доступна через отдельную форму GateBot. В «Интеграциях» режима Marketplace доступны статус и проверка связи. [Подробный порядок](YCLIENTS_MARKETPLACE.md).

Режим сохраняется в `yclients_connection_mode`. Для прежних филиалов без этого поля
используется сохранённый `yclients_connection_source`, иначе — `direct`. Явная
установка приложения может перевести прямое подключение в marketplace; обратная
подмена через форму входа запрещена. При `freeze`/`uninstall` переустановите приложение
через YCLIENTS.

## Авторизация по филиалам

Обычный пользовательский токен читается **только из зашифрованного подключения
конкретного филиала в SQLite**. `YC_USER_TOKEN`, `YC_COMPANY_ID`,
`YC_USER_TOKEN_<branch_id>` и `yclients_user_token_env` больше не участвуют в
runtime-авторизации. Старые значения в `.env` не используются даже для совпадающего
ID. Если сохранённого подключения нет, требуется подключить учётную запись.

`YC_PARTNER_TOKEN` остаётся общим ключом приложения. Для marketplace также нужен
`YC_MARKETPLACE_SYSTEM_USER_TOKEN`: это системный пользователь приложения, а не
обычный пользователь отдельного бизнеса. Его токен может быть одним для нескольких
установленных филиалов; локальное подключение, права и состояние установки всё равно
сохраняются и проверяются отдельно для каждого филиала. Он не подставляется
автоматически в филиал без подтверждённой установки.

После `uninstall`/`freeze` получение credentials и чтение филиала блокируются до
восстановления подключения. Отсутствующий токен вызывает локальную ошибку этого
филиала; другие филиалы продолжают синхронизацию. Чужие токены не подставляются.

## Чтение снимка

### Проверка подключения и прав

В интерфейсе подключения прямой токен заменён входом по логину и паролю YCLIENTS.
Поддерживается двухфакторный код; пароль и код не сохраняются. Ручное сохранение
токена через API недоступно администратору филиала. Маркетплейс остаётся отдельным
способом установки системного пользователя.

Для учётной записи карточка показывает имя и контакты пользователя из успешного
официального ответа `POST /auth` (`id`, `name`, `email`, `phone`, `login`). Разрешённые
поля профиля хранятся зашифрованно отдельно от статуса; токен и сырые ответы браузеру
не возвращаются. Для старого подключения без профиля нужно один раз повторить вход.
Кнопка «Проверить подключение» выполняет только GET-проверки прав и расписания;
данные профиля отражают последнюю успешную авторизацию.

Мастер проверяет официальный `GET /user/permissions/{company_id}`, затем одну запись
через `GET /records/{company_id}?count=1`. По документированной структуре прав нужны:
`timetable.timetable_access`, `timetable.timetable_phones_access`,
`record_form.record_form_access`, `record_form.record_form_client_access`.
Это права на журнал, телефоны в журнале и данные клиента в окне записи.
Планировщик может брать клиента из записи: право на всю клиентскую базу
`clients.clients_access` для одного чтения расписания не требуется. Но для поиска
ID по телефону в клиентской базе оно обязательно вместе с доступом к полным
телефонам. Назначьте пользователю доступ к базе клиентов, просмотру телефонов/email
и телефона в карточке; в диагностике прав используются `clients.clients_access`,
`clients.client_phones_access`, `clients.clients_phones_email_access` и
`clients.clients_card_phone_access`. Требования к видимости телефонов описаны в
[справке YCLIENTS о правах на клиентскую базу](https://support.yclients.ru/299/).
Маскированный телефон не подходит для безопасного сопоставления. Отсутствие этих
прав не блокирует чтение записей с доступными телефонами, но поиск ID завершится
ошибкой либо не найдёт доступного совпадения; локальный клиент и пропуск сохранятся.
Порядок проверки и исправления — [YCLIENTS_CLIENT_IDS.md](YCLIENTS_CLIENT_IDS.md).
Ограничения `master_id`/`position_id` должны разрешать всех сотрудников. Запросы
ограничены выбранным филиалом; записи и контакты не выводятся в диагностике.
Неполный ответ или отказ в правах не подтверждает соединение и не заменяет ранее
сохранённый токен. Успешный пустой список записей сам по себе не доказывает доступ
к телефонам клиентов. Если в проверенной записи клиент есть, но телефон скрыт
или отсутствует, соединение не подтверждается: нужно проверить номер и права.

В SQLite остаются время проверки и безопасные результаты: доступ к филиалу,
записям, контактам, всем сотрудникам и API записей. Ошибки авторизации, прав,
лимитов и связи различаются, сырые ответы не сохраняются. Проверка старого токена
не может затереть статус нового подключения. Контракт проверен по
[официальному API](https://developers.yclients.com/ru/) — раздел «Пользователь»,
таблица полей прав (`timetable_phones_access`, `record_form_client_access`) и
метод «Получить список прав» `GET /api/v1/user/permissions/{company_id}` с
категориями `timetable`, `record_form`, `clients` — и покрыт mock-тестами
`test_integration_connections.py`; реальные POST/auth к действующей CRM не выполнялись.

У автономных филиалов (`yclients_enabled=false`) подключение и выдача сохранённых
credentials запрещены. Для существующих филиалов отсутствие поля означает `true`.

Проверка подключения относится к чтению расписания. Если администратор выбрал
доставку уведомлений через YCLIENTS, дополнительно нужны права этого пользователя
на рассылку. Такая отправка реализована отдельным адаптером и не расширяет GET-only
allowlist reader. Выбор поставщика и ограничения — [MESSENGER_DELIVERY.md](MESSENGER_DELIVERY.md).

Записи читаются по страницам, с проверкой типов, ID записей, повторов, company_id и постоянства `total_count`. Неполная или противоречивая пагинация отменяет применение всего снимка филиала. HTTP/JSON/timeout ошибки отделяются от успешного пустого списка: сетевая ошибка не означает отмену всех записей.

Планировщик читает сегодняшние и завтрашние записи и охватывает предыдущие даты с возможным активным пропуском. Локальный таймер включает известный пропуск за два часа до записи с запасом 30 секунд для очереди уведомлений, включая предыдущий вечер для раннего визита. Срок задаётся в часах от начала визита, по умолчанию восемь. Удалённые записи и отметки неявки исключаются. При смене телефона клиента прежние привязки сбрасываются. [Правила выдачи и восстановления](APPOINTMENTS.md).

## Webhooks

Старый `webhook_handler.py` был закомментирован, а публичный endpoint сохранял произвольные headers/body без аутентификации. Эта цепочка исключена из runtime. Пока endpoint возвращает явный `503`, события webhooks не считаются обработанными и не дают права проезда.

Будущее восстановление требует подтверждённого контракта аутентификации источника, защиты от повторов и очереди. Даже после этого webhook будет поводом прочитать запись через разрешённый API, а не доверенным разрешением открыть ворота. Ни настройка webhook, ни изменение приложения в YCLIENTS не выполняются автоматически.

## Проверка

`tests/test_yclients_readonly.py` проверяет запрет любых write methods, разрешённые host/path, отсутствие redirects и все ошибки пагинации. `tests/test_scheduler.py` проверяет самостоятельность филиалов, приоритет ручных прав, отписку, неуспешные снимки и временные границы. Все HTTP-ответы в этих тестах искусственные; действующая CRM не используется.

`tests/test_yclients_modes.py`, `test_integration_sources.py` и браузерные проверки
покрывают разделение двух способов, привязку регистрации к браузерному контексту,
запрет подмены ID и ручной авторизации marketplace-филиала, приватность профиля и
отсутствие fallback на обычные пользовательские токены из окружения.
